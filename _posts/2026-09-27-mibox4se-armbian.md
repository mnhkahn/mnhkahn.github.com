我想把闲置的小米电视盒子变成一台能 SSH 登录、部署服务的小服务器。目标很明确：让 Linux 直接运行在板子上，后面再考虑装 Homebridge。

这一天，我们跑通了原生 Armbian：系统写入 eMMC，正常软件重启后能自行启动，自动连接 Wi-Fi，通过 SSH 运行服务。

这篇文章记录从识别主板、进入 FEL，到使用原厂 U-Boot 启动 Armbian 的实际过程。它是一次阶段性跑通记录，尚不是经过长期稳定性验证的通用刷机教程。

## 先看清手里这块板子

盒子外部型号是 **MDZ-23-AA**。拆开后，PCB 上能看到 **M20_V50**，以及日期 2018-08-23。后续 FEL 协议返回进一步确认，芯片是全志 H3。

右侧的 Kingston 芯片是 eMMC 存储，标识为 EMMC04G-M627。它承担持久保存系统和数据的工作；板上另有 NANYA 内存芯片。两者虽然外观都是黑色封装，作用不同。

这次正常启动的 Linux 报告约 991 MiB 内存。备份得到的 eMMC 用户区大小为 3,791,650,816 字节。FEL 临时引导阶段曾只识别出 512 MiB，后来正常启动才识别到约 1 GB，这提醒我们：启动参数不对，也可能表现为容量异常。

## 真正的突破，是看到 AWUSBFEX

前面花了不少时间区分 ADB、线缆连接和底层启动模式。ADB 能用，只能说明 Android 提供了调试通道；是否能从底层加载引导程序，还需要另一种验证。

这块板子最终成功进入 FEL，Mac 上运行 `sunxi-fel version` 得到了：

```text
AWUSBFEX soc=00001680(H3) 00000001 ver=0001 44 08
scratchpad=00007e00 00000000 00000000
```

这条协议响应，比“白灯亮了”“电视黑屏了”明确得多：电脑已经能与 H3 的 ROM FEL 通信。

但 FEL 可用不等于已经刷好了系统。后面还需要初始化内存、加载引导程序、启动内核，最后才能谈持久存储。我们也经历了 USB 上传成功、执行后没有画面的情况，必须继续用日志和控制台确认究竟走到了哪里。

## 用原厂 U-Boot，把 Linux 带起来

最初尝试自行编译 U-Boot，也试过直接跳进 Linux 内核。这些尝试没有形成可用的启动路径。真正跑通的链路，是保留原机的引导能力：

```text
H3 ROM FEL
    ↓
厂商 fes1：初始化 DRAM
    ↓
原机备份中的 U-Boot
    ↓
bootelf：执行辅助启动程序
    ↓
调用原厂 bootm：启动 Linux
    ↓
initramfs → Armbian 根文件系统
```

我们没有持久替换原厂 U-Boot。辅助 ELF 的作用，是调用它已经具备的启动命令，并补上这块板子运行 Linux 所需的参数处理。

有几个细节直接影响了能否启动。

**第一，定时器频率必须明确。** 通过内存保留日志，发现内核其实已经开始运行，却卡在 ARM timer 初始化附近。给 Linux 设备树的 `/timer` 加上 24 MHz 的 `clock-frequency` 后，才继续走到 USB 控制台。

**第二，要确认 bootm 实际使用了哪个设备树。** 原厂命令没有按预期采用传入的 Linux DTB。辅助程序修正内存中的设备树指针，再执行后续启动阶段，才让准备好的参数真正生效。

**第三，大文件的加载地址和回读方式都重要。** 启动包包含内核、设备树和 initramfs，需要避开搬移时可能覆盖的区域。最终将 ELF 放在 `0x48000000`，上传后回读比对 SHA-256。读取拆成小块，避免一个长 USB 请求超时。

我们还遇到过 USB 终端只回显、不执行命令的问题。改为将 `setsid sh -i` 直接绑定到 ttyGS0，才得到能真正执行 `uname`、查看日志的 shell。出现终端设备和得到可用终端，也不是同一件事。

## eMMC 和 Wi-Fi，各有一处关键修正

Linux 最初无法正常使用 eMMC。成功阶段的处理方法，是解绑 MMC 驱动，清除原厂引导遗留在 MMC2 时钟寄存器中的一个模式位，再重新绑定驱动。

具体涉及寄存器 `0x01c20090` 的 bit 30。此前较高频率下出现数据错误，最终限制到 **6 MHz**，读出的数据片段与原始备份匹配，之后写入根文件系统并做完整回读校验。

这里必须保留一个边界：这项修正当时有效，但在后来的故障中重复执行，仍无法识别 eMMC。它是成功经验之一，不是对所有存储故障都有效的修复命令。

Wi-Fi 的突破则来自供电顺序。XR819 需要先将 **PL7 拉高，等待 30 ms，再释放 PL0 复位**。调整设备树 overlay 和电源时序后，驱动加载了固件，`wlan0` 出现，随后完成无线连接和 DHCP。

这一步让盒子终于摆脱了只能靠 USB 控制的状态，可以通过同一个局域网登录。

## 什么才算这次“装成功了”

最终运行的是基于 Beelink X2 社区镜像适配的 **Armbian community 26.11.0-trunk.59 / Debian 13**，内核为 **6.18.54-current-sunxi**。它不是小米官方支持镜像，也没有验证所有硬件功能。

当时的验证不是只看见一个 shell，而是确认：

| 项目 | 实测结果 |
|---|---|
| 根文件系统 | `/dev/mmcblk0p1`，ext4 |
| PID 1 | systemd |
| 持久启动 | 正常软件重启后，启动 ID 改变，未再次从 Mac 上传启动包 |
| 网络 | Wi-Fi 自动连接并取得地址 |
| 远程管理 | SSH 密钥登录成功 |
| 服务能力 | systemd 临时服务执行并返回预期输出 |

原始验证输出包含：

```text
NATIVE_BOOT_VERIFIED
systemd
/dev/mmcblk0p1 ext4
active
```

*以上是验证记录中的相关行摘录；SSH 成功后又检查了根分区和服务状态。*

持久安装覆盖了原安卓数据分区、boot 分区中的启动负载，以及环境分区前 128 KiB。原厂 U-Boot 保留，`boot_normal` 改为读取 Linux ELF 并执行。根分区、启动包和环境变量均做了回读校验。

系统当时有 Python、curl、SSH、systemd、cron 等工具，具备部署服务的基本条件。但根分区只有约 1.9 GB，安装后剩余约 576 MB。Homebridge 还没有安装，不能把后续服务目标也算作完成。

## 这次跑通的范围

本次已经验证了 eMMC 根文件系统、正常软件重启、Wi-Fi 自动连接、SSH 登录，以及 systemd 服务执行。最关键的经验，是复用原厂 U-Boot，逐项修正定时器、设备树、eMMC 时钟和 Wi-Fi 供电顺序，再用回读校验和实际命令确认结果。

后续盒子出现失联，截至写稿尚未恢复正常运行，原因未定。因此，这次成功只能表述为“曾跑通”，不能据此宣称已经能够长期稳定地当服务器使用。Homebridge 也还没有安装。

原始备份、成功版本的启动负载和验证记录已经保存，后续工作从这些已确认的结果继续。
